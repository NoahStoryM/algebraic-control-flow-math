# Astra 对第五篇大纲调整的答复（2026-10-03 22:58 由 Noah 转来）

> 这一轮没有参考《Claude 的建议》。提问见 `咨询说明-大纲调整.md`。

我的判断是：**这条新主线成立，而且比旧稿更集中。真正需要调整的，是两次转折的动机，以及它们各自承担的任务。**

前两节已经让读者接受了“问题可以描述成一张表”，第三节又把表里的条件写成了程序。读到这里，读者自然会问：这几行代码怎样找出答案？以“实现这门语言”统领后文，确实接住了这个问题。

但第三节实际上提出了两项要求：

- 一组输入可以对应多个答案，语言要负责逐个寻找。
- 同一个未知项可以出现在多个条件里，语言要让这些条件共同确定它。

列表、`append-map`、延续和 amb 逐步解决第一项；未知项、代换与合一解决第二项。**这两项要求有共同的来源，却需要分别获得动机。** 如果把它们混在一起，容易给读者一种感觉：amb 已经解决问题了，作者又为了得到 miniKanren，添上了一套新设备。

结合前四篇来看，我觉得这个系列最有力量的地方，是已经写出来的程序不断提供下一步的理由。第四篇尤其如此：命名延续回应文本复制，传递调用者延续回应函数边界。第五篇也可以保持这种推进方式。中段让列表程序暴露“每一步都要处理一批结果”的负担；后段让直接风格程序暴露“值必须先得到，名字才能供后面使用”的组织方式。读者看见这些具体差别，便能理解每一次改写。

所以我赞成调整大纲，但**不建议把旧九节原样保留，只换连接句**。旧第四节需要拆开，旧第八节需要换入口。“认出剩余工作”和“擦除延续参数”的主体，则有很高的保留价值。

以下判断没有参考另附的《Claude 的建议》。

**1．中间那一段怎么接。** 你 22:49 的补充足以给“关系的复合”提供动机，但从复合走到 `for*/list` 与 `let*`，还需要一次观察：**接在当前结果后面的，可以是下一步，也可以是后面全部的工作。**

我会让这段经历三次很具体的变化。

先从第三节回到第一节的实际算法。`l ≤ a ≤ b ≤ c ≤ h` 可以通过依次选出三条边来满足。把每步要交给下一步的东西摆出来：

| 步骤 | 收到什么 | 每个候选交出什么 |
|---|---|---|
| 选 `a` | `(l h)` | `(a h)` |
| 选 `b` | `(a h)` | `(a b h)` |
| 选 `c` | `(a b h)` | `(a b c)` |
| 检查直角 | `(a b c)` | 原来的三条边，或没有结果 |

这里需要解释一次为什么带着那些分量：`a` 选出来以后，后面还要用；`h` 在选完 `c` 以前也不能丢。这样元组的形状就由实际计算决定，不像为了复合而临时设计的包装。

再把这些步骤写成返回列表的函数。随即出现旧稿里很好的观察：上一段交出一张列表，下一段只接受其中一项。由此得到 `map`，再由列表多套了一层得到 `append-map`，最后为这种连接取名 `∘ℒ`。

最后，把同样的步骤放回嵌套写法。旧稿“认出剩余工作”末尾的这条等式，正好承担这座桥：

```racket
(append-map g (append-map f xs))
=
(append-map (λ (x) (append-map g (f x))) xs)
```

在本文纯、有限的范围内，两边交出相同的列表。右边却让读者看见：交给外层 `append-map` 的函数，包含了后面连续的步骤。继续往里包，便得到“拿到一个 `a`，完成选 `b`、选 `c` 和检查的全部工作”。

**到这里，再拿出 `for*/list`，就有明确的辨认对象了：循环已经替我们把这段函数写好了。** 与 `let*` 的比较随后解释，两种绑定怎样使用这份工作。

因此我不会直接从“关系可以复合”跳到“循环长得像 `let*`”。中间要让读者看见，从逐段连接到嵌套 λ，传递的仍然是同一批候选。这一步旧稿已有材料，主要是调整位置和重心。

**2．整条主线成不成立，节次怎么排。** 成立。“实现这门语言”可以成为唯一的行动主线，但它不必成为每节反复宣布的理由。每节仍应回答眼前程序提出的问题。

我倾向于这样排。以下是内容分工，标题可以等正文写出来再定：

| 节次 | 内容 | 本节推进到哪里 |
|---|---|---|
| 01—03 | 保持当前安排 | 给出关系语言的第一段程序 |
| 04 | 用返回列表的函数表示关系；拆分挑边步骤；构造 `∘ℒ` | 小步骤可以接成完整搜索 |
| 05 | 从逐段连接转到嵌套循环；比较 `for*/list` 与 `let*`；得到 `choose/k` | 认出被反复调用的剩余工作 |
| 06 | 擦除延续参数；得到 `choose`、`fail`、`collect`；认出 amb | 用普通调用和复合组织多结果计算 |
| 07 | 尚未确定的值怎样共享；未知项、代换、合一 | 条件可以联系两个尚未确定的项 |
| 08 | 目标、合取、析取、`fresh`、`run*`；实现 `≤` 与 `pytho` | 第三节的程序真正运行起来 |
| 09 | 只要第一组答案 | 作为语言跑通后的短尾声 |

第七、八节分开，是为了让“为什么需要代换”和“内核怎么组装”各有被理解的时间。旧第八节里，这两件事挤在一起，前面还承担了重新引入关系语言的工作，负担比较重。

第九节可以保留。语言已经实现，使用者想少取一些答案，是自然的新问题。但应让第八节先有一次明确的兑现，避免第三节的承诺一直被拖到全文最后。

**3．有方向的函数，怎样走到未知项与合一。** 我建议不要把这个过程写成“逐渐消除函数的方向”。底层程序始终有运行方向，改变的是它处理的东西。

开始时，函数接收一组确定的数，交出另一组确定的数。实现关系语言时，条件接收的是**当前已经知道的信息**，交出加入这个条件以后得到的信息。

这正好解释：

```racket
Goal = Substitution → Substitution
```

这个类型最好在读者已经看过“信息怎样增加”之后出现。

例如，先要求 `x` 与 `y` 相等，再得知 `y` 是某个数。第一步没有一个现成数值可供传递，却也不是毫无所得：我们已经知道，两处必须指向同一个答案。程序需要把这件事记住。

于是自然得到以下过程：

- 未知项先有一个可以共享的身份。
- 目前知道的信息另外保存。
- 新条件读取这些信息，补充联系，或发现矛盾而失败。
- 最后根据保存的信息读出查询项。

这样，输入输出的方向落在“信息的传递”上；关系参数中的哪一项已知、哪一项未知，则成为另一件事。

还有一句应该在从列表函数转向关系语言时说清：**返回列表的函数已经提供了一种查找方向，但第三节的参数位置并不直接等于这个函数的输入输出位置。** 有了这层区分，读者不会期待一个 `p → List q` 经由 amb 就自动获得反向查询能力。

**4．合一的动机从哪里来。** 我同意你的判断：直角三角形这道题，用 amb 已经解决了。正文应该坦然承认这一点。

接下来的理由是：第三节希望写出的那种语言，还要允许条件之间共享未知项。为说明这件事，**值得暂时换一个很小的结构例子**，不必强迫三角形承担全部动机。

我会把旧稿后面的 `swapo` 提前使用。先不急着给代码，写出它要表达的两件事：

- `p` 是由 `x`、`y` 组成的二元组。
- `q` 是由同一个 `y`、`x` 组成的二元组。

给定 `p`，可以确定 `q`；给定 `q`，也可以确定 `p`。还可以先建立这些联系，稍后才确定某个分量。

普通模式匹配很适合从已知的二元组里取出分量。但这里，待匹配的东西本身也可能未知，而且两边可能都含有未知项。**我们需要一种能在两边之间补充信息、保存联系的匹配。** 到实际操作已经出现，再认出这是合一。

这条路线比旧稿的 `independent` 例子更有说服力。把同一个 `a` 故意拆成 `a₁`、`a₂`，熟悉 Racket 的读者很容易回答：“那就别拆，用同一个绑定。”旧稿随后也承认这一点，于是开头展示的失败，没有直接导出真正需要的新能力。

用 `swapo` 加上“先联系两个未知项，后确定其中一个”的小例子，缺口会更清楚。它们也不涉及算术求解，能够让读者先看清合一本身在做什么。

**5．𝒮、ℒ、ℛ 的联系讲到什么程度。** 我会保留这层结构，但放在 amb 已经造出来以后，作为对现有代码的整理。讲清三件事就够了：

| 写法 | 一步计算怎样交付结果 | 后续步骤怎样接上 |
|---|---|---|
| 𝒮 中的普通函数 | 交出一个值 | 普通调用或 `∘` |
| ℒ 中的函数 | 交出一张结果列表 | `append-map` 或 `∘ℒ` |
| ℛ 中使用 amb 的过程 | 每条成功分支交出一个值 | 普通调用或 `∘`；边界处收集 |

其中最值得展示的，是你旧稿已经建立的事实：**原本接不上的普通 `∘`，现在又接上了。** 这比先摆三个世界的定义更有力量。

然后给出列表写法与 amb 写法的两个转换方向：

```racket
(fℛ x) = (choose (fℒ x))

(fℒ x) = (collect (λ () (fℛ x)))
```

再用同一组挑边函数说明，转换也保留了它们接起来计算的方式。这样三者的联系已经足够具体，不需要增加一轮抽象理论。

这里有两点会影响读者理解：

第一，“有了 amb，任意函数都是二元关系”不是这一段最有辨识度的发现，因为第二节已经说过普通函数是关系。新得到的是：**沿用普通函数的调用写法，一次输入也能有零个或多个成功结果。**

第二，ℛ 如果表示使用 amb 的计算世界，就不要在后面又让同一个记号直接表示“接收两个项、返回 Goal 的关系接口”。两层程序有关联，但读者需要知道自己正在看哪一层。

列表与 amb 的对应可以保留答案的顺序和重复；把结果理解为数学关系时才忽略它们。沿用旧稿那一个倒序例子交代即可，不必把这里扩成独立的大节。

**6．旧第四节还要不要。** **内容需要，原来的整节不需要。**

我会这样拆：

| 旧第四节的材料 | 新位置 |
|---|---|
| 按挑边顺序拆出四个关系 | 新第四节，提供列表函数的实际对象 |
| 关系复合的数学定义 | 新第四节，紧邻两步连接的具体观察 |
| `fresh` 与相等约束 | 新第七、八节，等未知项确实需要它们时引入 |
| 关系语言里的四段复合版三角形程序 | 不再作为前半篇必经步骤；需要时在语言跑通后简短回看 |

数学定义不必很重。看过前两步以后，指出：边界与一个部分解相关，是因为存在一个中间的 `(a h)`，能让前后两段同时成立。随后写一般形式：

(S ∘ R)(x, z) ⇔ ∃y. R(x, y) ∧ S(y, z)。

紧接着，列表实现就回答“怎样得到这些中间项”：前一段把它们列出来，后一段逐个接着算。

旧稿先给 `fresh`、`==`、`Goal`，再展示第二版完整程序，之后才回到列表实现，读者会同时欠下很多尚未解释的东西。新主线已经有第三节那一段伪代码作为目标，不必在实现开始前再建立第二套目标程序。

**7．03 要不要加内容。** **可以小补，但我不觉得它短就是问题。** 这一节已经完成了很明确的变化：把集合里的条件搬到代码里，把找答案的责任交给语言。

我只会补清两处。

一处是名字的共享：`a` 在 `≤` 和 `pytho` 中出现，指的是同一个尚未确定的数，两行条件要由同一组 `a`、`b`、`c` 同时满足。这是后面代换的真实来源，可以先让现象出现，不必提前解释实现。

另一处是把结尾落到一个具体问题上：程序只写了条件，答案中的数究竟从哪里来？下一节便可以检查“把整张表存起来”的想法，再走到按输入计算所需行的函数。

你提出的 `add1` 例子足够完成这个过渡，一两句即可。它要说明的是**无需先枚举整张表，也能计算需要的行**。随后马上回到已有的 `right-triangles`，读者会认出：返回列表的表示开篇就已经出现了。

我不会为了充实第三节而加入 `fresh`、类型表或第二版程序。这里留一点空间，有利于读者真正记住那两行关系代码。

**8．限制在哪里说、说到什么程度。** 我建议分两次交代，分别解决预期和使用问题。

第三节只给一个轻量的范围说明：这次查询给定边界，寻找三条边；参数里允许出现未知项，不意味着每个关系都能在任意已知条件下求解。不要在这里展开调度和算术实现，但也别让读者形成“随便交换条件、随便留空参数都一样能跑”的预期。

真正的使用要求，放在第八节 `≤` 与 `pytho` 的定义旁边：

- `≤` 运行时需要已知的两端，用它们限定候选范围。
- `pytho` 运行时需要三条边已经确定，才能调用 `pyth?`。
- 因而这段程序先生成候选，再检查直角条件；交换两行不受当前实现支持。

最值得说清的是：**数学条件的合取没有先后，当前程序寻找答案却有先后。** 合一让未知项之间的联系可以保留下来；它不会自动把 `pyth?` 变成一个能处理未知数的算术求解器。

正文在这里解释到读者能够判断“这两行为什么按这个顺序写”就足够了。不必展开其他系统怎样调度或求解，否则刚刚兑现的语言实现又会被一组新问题冲淡。
