**1．四个范畴及其联系：【必须改】“继承”的推理方向；【建议】限定等价范围**

`Host_amb ≃ Kl(List)` 可以作为本篇的语义模型，但不能直接指完整 Racket 中所有形如 `a → b` 的过程。至少需要限定：

- 搜索有限且终止，底层计算没有另外的可观察效应。
- `choose` 使用可重复调用的定界延续。
- 外部按 `collect` 收集的列表观察计算，包括顺序与重数。
- 使用者通过规定的接口操作非确定性，不任意干预实现所用的控制边界。
- 若允许高阶参数与结果，需要相应的效应语义；本篇先在一阶数据上解释就够了。

两个方向可以明确写成：

```racket
(define ((reify-arrow f) x)
  (collect (λ () (f x))))

(define ((reflect-arrow g) x)
  (choose (g x)))
```

其中 `g` 是纯的列表箭头。`reify-arrow (reflect-arrow g)` 返回原来的列表；另一个方向在上述受限语言的观察等价下理解。Filinski 的表示结果支持这条路线，但不是完整宿主语言里任意过程之间的无条件同构。:chatgpt-content-reference{index="0"}

`Kl(List) → Rel` 的描述基本正确：取支撑、保持恒等与复合、不忠实，输出关系都是像有限的。还要区分数学模型与实际程序：Racket 可实现的箭头也受可计算性限制。

**不能由关系侧的等式成立，反推出列表侧逐字成立。** 忘掉顺序与重数的映射恰恰不能反映这些等式。

正文可以说：

> 关系的复合满足这些规则。现在检查列表的实现：即使把答案的顺序和重复次数也算进去，这些等式仍然成立。

四条规则确实成立，但依据是 `list`、`append-map` 的定义；关系侧提供的是设计要求与解释。

准确的对应是：

| 第二篇 | 第五篇 |
|---|---|
| 构造性宿主 𝒟 | 纯函数 Host |
| 带控制效应的直接风格 𝒞 | 带 `choose` 的 Host_amb |
| 延续的 Kleisli 世界 𝒦 | 列表的 Kleisli 世界 |
| 经 `flip` 与 𝒦 无损互转的 𝒰 | 当前没有对应物 |
| 当前没有对应物 | 忘掉顺序与重数后的 Rel |

**Rel 不对应 𝒰。** `flip` 是无损改写，取支撑会丢失信息。

可以说“两篇都在直接风格与显式编码之间往返”，不能说这里三个世界又构成第二篇那个同构三角形。这个修正也应同步到第六篇大纲。

**3．谓词复合的论证：【建议】保留黑盒论证，收紧不可计算性的说法**

“搜索由谁承担”很准确。关键是：

> 只给两个谓词，没有中间类型的枚举方式，也没有其他结构，写不出通用的关系复合程序。

数学上的存在量词没有问题；作为子集之间的操作，沿投影取存在确实是逆像的左伴随。

计算上的障碍也成立：在自然数上，即使谓词本身可判定，对它求存在也可能不可判定。例如“程序在第 `n` 步以内停机”可判定，对 `n` 求存在就涉及停机问题。

但两处不要说得过满：

- 不要求整个 `Y` 有限；能为当前输入找到**有限且完备的候选范围**也足够。
- 已知谓词的具体结构时，可以用代数求解、约束传播等方法，不必穷举。

另外，**`fresh` 本身不负责搜索**。它引入未知项；在原型里，真正枚举候选的是 `betweeno` 中的 `choose`。草稿“找中间项的搜索，交给了 `fresh`”建议改成“中间项由 `fresh` 引入，如何找到它交给这些目标的运行”。

**4．关系语言的数学结构：【必须改】quantale 的层级及“并”的含义**

几项分别看：

- **Rel 是 quantaloid，亦即以 `Sup` 充实的范畴。** 每个 hom 是完备格，复合分别保持任意并。每个端同态集合 `Rel(X,X)` 才构成 quantale。直接称“quantale 充实的范畴”不够准确。
- **列表侧的 `disj` 是有序追加。** 取支撑后才成为关系的并；原层面不交换、不幂等。
- **列表复合只有一侧分配，正确。** 设 `+` 表示逐点 `append`，则
  \[
  h∘_\mathcal L(f+g)=(h∘_\mathcal L f)+(h∘_\mathcal L g).
  \]
  另一侧一般不成立：两边可能分别产生 `(a b a b)` 与 `(a a b b)`，已实际验证。
- **关系取逆的解释正确，但“没有 †”要区分语义与实现。** `betweeno` 所描述的数学关系当然有逆关系；现有程序没有实现所有方向的求解。有限像关系的逆还可能不再像有限。
- **状态与非确定性的叠法正确。** 这里是各分支拥有各自代换的回溯状态，形状为 `Subst → List Subst`；作为返回单位值的状态计算，是 `StateT Subst []` 的特例。

**5．`run 1` 与 layered monads：【建议】作为动机成立，不能作为必要性证明**

把它归入“多个效应分别表示后怎样共同运行”的问题，是合适的。Filinski 1999 处理的确实是多层效应的表示。:chatgpt-content-reference{index="1"}

不过，这个失败直接证明的是：

> 当前这个按最近边界退出的 `abort`，没有实现退出整个搜索的意图。

它没有证明 `run 1` 必须用多 prompt 才能实现。捕获外层逃逸延续、改变答案协议、使用可暂停的搜索，都可能解决它。

“一套定界不够两种意图用”可以作为现场感受；一般结论应收紧为“现有接口没有区分这两种退出目标”。

**6．公平合取的结合律：【建议】有限、纯的情形下，你的判断正确**

常见交错合取**不保持答案顺序意义下的结合律**。忽略顺序、按答案多重集比较，有限纯计算可以恢复这条等式。LogicT 论文专门区分了这两种观察标准。:chatgpt-content-reference{index="2"}

这是实际运行过的有限版本反例，用来检查交错产生的次序：

```racket
(define (interleave xs ys)
  (if (null? xs)
      ys
      (cons (car xs) (interleave ys (cdr xs)))))

(define (bindᵢ xs f)
  (if (null? xs)
      '()
      (interleave (f (car xs)) (bindᵢ (cdr xs) f))))

(define (f x)
  (list (* x 10) (add1 (* x 10))))

(bindᵢ (bindᵢ '(1 2) f) f)
;; => (100 200 101 110 201 210 111 211)

(bindᵢ '(1 2) (λ (x) (bindᵢ (f x) f)))
;; => (100 200 110 210 101 201 111 211)
```

两边排序后相同。但不要把这个结论推广为所有无限搜索、所有“公平”调度都成立：还涉及能否暂停、是否持续产出、有没有其他效应。

这部分适合留在创作者笔记，不必进入第五篇正文。

**6½．多元关系、二元关系与合取：【必须改】“复合等于取交”的对象**

前两点成立：

- Rel 的 compact closed 结构支持对同一张关系表重新划分输入、输出。
- (a) 是共享变量的合取查询，(b) 是链式复合。
- 为了接成链，要把后面需要的列一路带下去，这是中间元组很好的解释。

但下面这句需要改：

> 对这类关系，依次复合等于约束取交。

**取交的是约束的解集，不是 `Subst → Subst` 关系本身。**

例如“令 `x=1`”与“令 `y=2`”，分别运行得到不同代换；两条代换关系直接取交，与先后运行得到 `{x=1,y=2}` 不是同一个操作。

可以用一个充分条件说清楚。令 \(D(s)\) 表示代换 `s` 允许的完整赋值集合。若目标 `g` 正确、完整地实现约束 \(\varphi\)，则要求：

\[
\bigcup_{t\in g(s)}D(t)=D(s)\cap\llbracket\varphi\rrbracket.
\]

后面再运行实现 \(\psi\) 的目标，就得到：

\[
D(s)\cap\llbracket\varphi\rrbracket\cap\llbracket\psi\rrbracket.
\]

这里还需隐藏局部变量，忽略重复答案，并按代换的意义比较，而不是比较哈希表的具体写法。

**不建议用“每个目标都是闭包算子”来补救。** 一般目标会分支、失败，不是单值闭包算子；单调、扩张、幂等也不足以保证两个闭包算子交换。

正文一句就够：

> 前一个目标交出满足自身条件的代换，后一个在这些代换上继续求解；最后留下的答案，就同时满足两个条件。

**7．“列表模拟关系”：【建议】基本准确，换掉“过于忠实”**

列表多记录顺序与重数，`run*` 返回列表，这两点都对。

“模拟得过于忠实”容易让读者误以为这些信息原本属于关系。更准确也更有观察感的是：

> 作为关系，它们没有区别；作为列表程序，它们还记着答案以什么顺序、出现了几次。

另外，有限个答案与搜索能够终止不是同一个条件。本篇的“有限搜索”最好指整个搜索过程能够完成。

**8．数学对应表：【必须改】区分目标、控制操作与答案表示**

建议按下面的含义理解：

| 写法 | 数学意义 | 限定 |
|---|---|---|
| `succeed`，或 `(conj)` | ⊤ | 恒等目标 |
| 失败目标，或 `(disj)` | ⊥ | 不产出代换 |
| `==` | 项的等式约束 | 通过合一求解 |
| `conj` | ∧ | 按解集解释 |
| `disj` | ∨ | 列表层面保留重数、顺序 |
| `fresh` | ∃ | 引入局部变量，观察时隐藏 |
| `run*` | 查询、收集解 | 结果表示为列表 |

尤其注意：原型里的 **`fail` 是零参数控制操作，不是 `Subst → Subst` 目标**。把这个过程直接传给 `conj` 会有参数个数错误。表中最好写“失败目标”，或直接用 `(disj)`。

还有两个边界：

- `walk*` 没有实现未绑定变量的规范化命名；例如查询未确定的 `q`，现在得到的是 `#<var>`，不是列出所有具体取值。应限定本篇展示的最终答案都已确定，或补一个简单的答案重整步骤。
- v4.1 笔记说 `(run* () …)` 只会得到 `'(())` 或 `'()`，**在列表层面不成立**：多条成功路径会得到 `'(() ())` 等。取支撑后才只有两种。

**9．是否点破状态与非确定性：【建议】说实现事实，暂不下定义**

可以写：

> 每条分支带着自己的代换往下走；一条分支失败，不会改动其他分支手里的代换。

这句话既解释回溯状态，也对读代码有帮助。

“逻辑式编程是状态与非确定性的组合”则概括过大：普通状态加非确定性不会自动产生逻辑变量、合一与关系语义。若要命名，写成“这个实现把代换状态与非确定性搜索接在一起”。

**10．`kernel.rkt`：【必须改】`fresh`；其余简化需要明确范围**

当前勾股例子都能运行，`conj` 的 `foldl` 顺序也正确。主要问题如下。

**第一，`fresh` 在构造目标时创建变量，导致重复使用同一目标时共享变量。**

在原型后追加：

```racket
(run* ()
  (let ([g (fresh (x)
             (disj (== x 1) (== x 2)))])
    (conj g g)))
;; 当前 => (() ())
```

如果每次运行 `g` 都引入新的局部变量，两次独立二选一应当产生四条成功路径。

建议改为：

```racket
(define-syntax-rule (fresh (x ...) g ...)
  (λ (s)
    (let ([x (var 'x)] ...)
      ((conj g ...) s))))
```

修改后实际得到：

```racket
'(() () () ())
```

μKanren 的 `call/fresh` 同样在目标收到状态以后才分配变量。:chatgpt-content-reference{index="3"}

**第二，同一个修改也解决了常见递归关系在构造时提前展开的问题。**

例如通常写法的 `appendo`，递归调用位于 `fresh` 主体里。当前宏立即求值这个主体，查询还没开始就继续构造递归目标。我实测原版在限定时间内无法返回；改成上面的宏后，`appendo '(1) '(2)` 正常得到 `'(1 2)`。

这不意味着任意位置的递归调用都自动安全，但足以说明延迟主体不是可有可无的优化。

**第三，没有 occurs check，不等于支持循环项。**

```racket
(run* ()
  (fresh (q)
    (== q (cons 'a q))))
;; 当前 => (())
```

在有限树的项模型中，这个约束没有解；当前实现却接受。若把 `q` 输出，`walk*` 又可能无限递归。

可以不实现 occurs check，但应明确：

> 本实现只处理不会形成循环代换的查询。

若希望 `==` 对所有有限树输入都保持逻辑上的正确性，就应补检查。

**第四，`pytho` 与草稿承诺冲突。**

草稿写：

> 当 `c` 还未知时，前者会把它找出来。

但实际运行：

```racket
(run* (c) (pytho 3 4 c))
```

会在乘法处收到 `#<var>` 而报错。这不是将来才需要交代的细节：§2 的承诺与 §5 的兑现直接冲突。

建议 §2 只说“参数可以包含未知项，由整组目标共同求解”；不要承诺这个 `pytho` 单独具有反向求解能力。

**第五，零参数 `∘ℛ` 没有实现。**

当前 `(∘ℛ)` 会匹配失败。若希望与普通 `compose`、`∘ℒ` 对齐，补：

```racket
['() (== x z)]
```

否则明确它只接受至少一支关系。这是【建议】，不影响现有四段关系的例子。

**11．`run1.rkt`：【建议】例子保留，解释再落到等待的工作上**

已经复现：它返回全部六组边。

解释正确：`choose` 调用的 `k` 自带 `reset`，分支中的 `abort` 结束这次局部计算；外面的 `append-map` 仍有其他备选要处理。

一个值得指出的细节是：**原型中 `abort` 已经处于该局部计算的尾位置**。去掉它也会得到同样的答案列表。这正说明它没有触及真正想丢弃的工作。

正文可以落在：

> 它结束了当前备选的计算，却没有丢弃等待其他备选的 `append-map`。

不必换题材；“找一组三角形就够了”比另造 `boom` 更自然。

若需要最小机制验证，我运行过：

```racket
(reset
  (let ([x (choose '(1 2 3))])
    (abort (list x))
    (error 'unreachable)))
;; => (1 2 3)
```

后面的错误确实被跳过了，其他备选却照常运行。

**12．公平性的两句话：【建议】保留实现层面的限定**

“这份实现深度优先，所以无限左分支可能饿死右边”正确。

“前沿就是宿主栈，所以不公平”因果上略粗。真正决定顺序的是：

> `append-map` 要等当前备选的后续计算全部完成，才处理下一个备选。

“前沿不能再是宿主栈，得自己维护”也应改成“不能继续完全依赖当前这种调用顺序”。可以保存可暂停的延续，未必必须换成显式队列。

“惰性列表用 `append` 仍不公平，公平靠交错”基本正确；补充在创作者笔记即可：交错要求分支能在适当位置让出执行权，一个不暂停也不产出的死循环仍可能卡住调度。

**13．与 `call/cc` 版 amb 对照：【必须改】把“需要”限定到具体实现**

可以说：

> 那几份实现用可变的 frontier 记录待探索分支；这一版让 `append-map` 的调用过程保存这些等待。

不能据此说所有 `call/cc` 回溯实现都必须使用可变全局 frontier。显式成功／失败延续也能承担回溯工作。

另外，“定界延续版纯”建议改成“这一版没有显式可变状态”。`choose` 本身仍是控制效应，只是被 `collect` 封装后可以表现为纯的列表计算。
