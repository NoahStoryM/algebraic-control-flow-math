有两处需要实质修改，另外几处补一个局部限定就够了。

1. **【必须改】函数复合的中间项，不是对任意 `x、z` 都恰好存在一个。**

   §4：

   > R 与 S 都是函数时，这样的 y 恰好有一个……

   上文的“这样的 y”同时满足 `R(x,y)` 和 `S(y,z)`。固定 `x、z` 后，如果 `z` 不是复合函数的结果，就没有这样的 `y`。

   改成下面这个意思即可：

   > R 与 S 都是函数时，给定 x，R 唯一确定 y，S 再唯一确定 z，得到的正是函数的复合。

   关系复合的定义和谓词不能通用复合的论证，其余部分成立。

2. **【必须改】§6 末尾混同了“下一段函数”和“全部剩余工作”。**

   > `append-map` 收到的那个函数，不管是手写的一段 `pick-bo`，还是……都是同一样东西……

   当前 `∘ℒ` 用的是：

   ```racket
   (foldr append-map (list x) f*)
   ```

   它先得到全部 `(a h)`，对它们运行 `pick-bo`，再把得到的全部 `(a b h)` 交给 `pick-co`。所以这里的 `pick-bo` **只包含下一段工作**，没有包含随后挑 `c`、检查勾股条件的工作。

   CPS 版的 `k` 则包含整个后续计算：一个 `a` 下面的搜索完成后，才轮到下一个 `a`。我运行核对了，两种写法的结果相同，执行步骤的次序不同；包里的验证代码其实也已经记录了这个区别。

   这里可以借上一节的结合律把联系讲准：

   ```racket
   (append-map g (append-map f xs))
   =
   (append-map (λ (x) (append-map g (f x))) xs)
   ```

   在本文纯、有限的范围里，两边交出同一张列表。**把后续各段一起包进函数以后，这个函数才承载全部剩余工作。** 正文可以只点明这一步，不必展开新的执行日志，也不需要修改 `∘ℒ`。

3. **【需要限定】三种绑定写法的等式，当前针对列表。**

   §6 把 `for/list` 改写为 `map`，对本文的 `inclusive-range` 成立，但对一般 Racket 序列不成立。例如：

   ```racket
   (for/list ([v #(1 2)]) v) ; => '(1 2)
   (map values #(1 2))      ; 报错：要求列表
   ```

   在并排等式之前说明“这里的 `e*` 都是列表”即可，不必介绍一般序列的实现。

4. **【需要限定】amb 的第二条转换等式，要说明按收集结果比较。**

   三行宏在当前例子中成立，两条转换也有对应测试。建议在等式后补一句：

   > 第二条说的是，把任一边放进同样的后续计算，再由 `in-amb` 收集，会得到同一张列表。

   这就解释了直接风格表达式之间的 `=`。无需在这里引入新术语。

   “amb 这个‘容器’不是一个值”的意思也能理解，但更准确的落点是：**调用处拿到一个结果，全部结果由边界上的收集操作交出。** 你包里的 `in-amb` 确实返回惰性流，正文已经明确区分它与这里的一次性列表实现，这一点没有问题。[docs.racket-lang.org](https://docs.racket-lang.org/amb/index.html?utm_source=chatgpt.com)

5. **【小修】“表”和“列表”的区别，在 §7 又合到一起了。**

   > 表，是把所有走通的时间线并排摆出来的样子。

   不同时间线可以交出相同的答案。我用当前内核运行：

   ```racket
   (run* (x)
     (disj (== x 1) (== x 1)))
   ;; => '((1) (1))
   ```

   因此，并排收集所有成功时间线，直接得到的是**答案列表**；忽略顺序和重复以后，才得到关系的表。这里沿用 §2 已经说清的区别即可。

   同节“主体里没有列表了”也应收窄为“不再需要把成功结果额外包成单元素列表”：主体里仍然有备选列表和表示三条边的 `(list a b c)`。
